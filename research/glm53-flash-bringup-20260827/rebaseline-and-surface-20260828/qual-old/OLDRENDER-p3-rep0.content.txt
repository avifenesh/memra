Looking at what you've described, the root cause chain makes sense — venv deletion while a live process held mmap'd code pages, subsequent lazy `open()` failures on venv-resident files. The `ssl.create_default_context` deducing `certifi/cacert.pem` as the trust store path is a well-known failure mode when `CERTIFI_PATH` can't be resolved from a deleted install.

A few things worth flagging on the paths you didn't take:

**On systemd vs. tmux:** you're right that tmux won't survive reboot, but there's a subtler issue worth knowing — a tmux-hosted process also inherits the tmux server's environment. If you ever launch the gateway from a shell with different `PATH`, `PYTHONDONTWRITEBYTECODE`, or locale vars than a fresh boot would produce, you get environment drift that only manifests as mysterious differences between "session" and "clean start" behavior. User-level systemd units (`~/.config/systemd/user/`) give you a deterministic environment — that's the stronger argument beyond just reboot survival. `Restart=on-failure` with `RestartSec=5` would also handle the crash-restart case automatically rather than needing you to relaunch. One caveat: user units don't run if that user has no active session unless you enable `loginctl enable-linger <user>` — if your box reboots and nothing forces your user session to spin up, the unit stays cold until you log in. Linger fixes that.

**On the error-surface fix in `gateway/run.py:7152`:** yes, `FileNotFoundError.__str__` only gives you `[Errno 2] No such file or directory` with the filename omitted when constructed with just errno — but when raised from `open()` it normally *does* include the path. The fact that you lost it suggests the catch-all is interpolating `str(e)[:300]` after an exception re-wrapping that drops `filename`. Beyond adding `getattr(e, 'filename', '')`, consider `repr(e)` for the fallback path — it suppresses nothing and makes type-mangled errors (`json.JSONDecodeError` losing its positional args, for instance) self-evident. Keep `str()` for the primary log line since it's human-readable, add `repr()` as second-level detail.

**On the lockfile cutoff vs. `--frozen`:** your diagnosis is backwards from what's usually the issue. `--frozen` skips the *update* check of the lockfile against `pyproject.toml` — it still uses the lockfile as-is. The mistake a future-you will make is treating `--frozen` as a resolver bypass when a runtime dependency changes; it's a check-skipper, not a resolve-skipping trick. If you hit a case where you genuinely need a fresh resolve (not just an env rebuild), the move is bumping `exclude-newer` in the lockfile's `[[tool.uv.index]]` config or the `UV_EXCLUDE_NEWER` env var, then running `uv sync` without `--frozen`. The mistralai resolver failure with Python 3.14 in the supported set is its own issue — likely a `python_requires` mismatch on the pinned mistralai version in your lockfile, and the real fix is either bumping the pinned version or dropping 3.14 from `.python-version` rather than repeatedly papering over with `--frozen`.

One operational note: the old PID (3879941) being in a ghostty terminal scope was a real liability even without the crash — if you'd closed that window, the SIGHUP might have taken down the gateway mid-task. Worth checking whether anything else in `~/.hermes/` has the same launch pattern.
