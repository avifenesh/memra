ONE CORRECTION, because it is an easy over-fix: `structured_output: false` is CORRECT and
DELIBERATE here, not under-advertising. This template opens its think tail unconditionally
and carries no enable_thinking switch, so the server 400s `response_format` BY NAME, and
this lane's battery reproduced that refusal (case 08a). Commit 025c7d4314 flipped the row
to false precisely because advertising true was a claim the server itself refuses. Whatever
is done about the other three models, do not "fix" this row to true: it would restore the
dishonest claim. The comment at main.rs:5497 says exactly this.

WHAT THIS BOX CANNOT SETTLE, stated so it is not read as a clean bill of health.
`GET /v1/models` and `GET /v1/models?schema=openrouter` return BYTE-IDENTICAL payloads on
this server (both sha 5d8f878e41005a21). The Provider Monitor row is not produced at all:
`supported_parameters`, `json_mode`, `structured_outputs`, `tools` and `tool_choice` are
ABSENT as top-level fields, and the only capability information is the nested
`capabilities` object shown above. So the `parameters` map built at main.rs:5109, which is
where `json_mode` / `structured_outputs` / `tools` / `tool_choice` are inserted, never
appears in what this server serves.

The confound, and why that is not evidence about production: this server was launched from
a bare `MEMRA_MODELS=` env mapping with NO models.toml and therefore NO OpenRouter metadata
(no `openrouter_slug`, no pricing, no sampling defaults; `pricing.input` is null and
`chat_defaults=None/None` for the same reason). Production has that metadata and this box
does not, so the provider-feed SHAPE here is not comparable to the feed prod serves. The
under-advertising seen through api.tiyuvta.ai therefore stays OPEN and needs a box running
the real models.toml to settle; it cannot be closed from this receipt.

NO capability code was read into, changed, or proposed to change in this lane. This is a
product-claim surface and the fix is the owner's call.
