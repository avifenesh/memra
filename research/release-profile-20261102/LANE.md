# Release profile A/B: Cargo defaults vs opt-level 3 + fat LTO + one codegen unit

Question: what does adopting the owner's standard release profile (`opt-level = 3`, `lto = "fat"`,
`codegen-units = 1`) change in memra, and does it change any result? Decision record:
[docs/decisions/RELEASE-PROFILE.md](../../docs/decisions/RELEASE-PROFILE.md).

Scope: one source tree (`527b946784`, the `spark-sm121` tip, which contains `main`), one rig (the
RTX 5090 Laptop and its laptop CPU), 2026-11-02, platform power profile `balanced` on every run
(recorded per row). Arm A is Cargo's default release profile. Arm B passes the three settings as
`--config profile.release.*` on the same checkout, so both arms build identical sources into
separate target directories. Serving cells use Qwen3.5-9B NVFP4 MTP GGUF.

Method:

- Builds: `measure_build.py` runs each build under the shared rig build lock at `nice -n 15` with
  `CARGO_BUILD_JOBS=2`, `RUSTC_WRAPPER=""` (no sccache) and `MEMRA_CUDA_ARCH=120a`, timed by
  `/usr/bin/time -v` inside the lock, with a 500 ms sampler of compiler RSS, used memory and core
  temperature (`samples/`). Cold builds delete the arm's target directory first. Order: cold A1 B1,
  touch rebuilds ABBAAB, test builds A then B, cold B2 A2 A3 B3, workspace bins A then B.
- Serving: `host_bench.py` boots each arm's `memra-server` under `gpulock` and the build lock
  (no build heats the CPU during a round), rounds ABBAAB. Per round: boot to `/health` 200, 20
  timed `/v1/tokenize` calls on a frozen 46-message, 165,525-token chat (`make_longchat.py 540000`
  over repo docs), 30 streamed short cached-prompt requests (TTFT and E2E), three greedy 512-token
  streams and two seeded (1234) sampled 256-token streams. `queue5.sh` adds six tokenize-only
  rounds of 60 calls with server CPU time per call.
- Correctness: CPU crate suites and the engine lib suite run with `cargo test --release` in each
  arm (`CUDA_VISIBLE_DEVICES=""`); `cpu_native_check` against the same companion library; fatbin
  and archive hashes compared (`fatbins-A.txt`, `fatbins-B.txt`, device ELFs via
  `cuobjdump -xelf all`).

Results: [SUMMARY.md](SUMMARY.md) (generated by `summarize.py` from `results.jsonl`,
`host_results.jsonl` and `host_tok_results.jsonl`). Raw logs are under `logs/`, the streamed
texts under `streams/`.

Hosted CI job times: [CI-HOSTED.md](CI-HOSTED.md). Under fat LTO the `build` job went from 12 to
18 min to 59.6 min, just under its 60-minute timeout. With the CI-only override back to Cargo's
default optimization, it took 18.7 min.

Not measured here: a PRO 6000 or B200
host, and a GGUF-only load path separate from boot. The worker thread spins on GPU completion, so
its CPU time equals decode wall time; the decode cells report wall time, not a CPU split.

Verdict: serving flat, except tokenization, which is 6.3% faster in the 60-call rounds. Every
correctness surface is byte-identical. The binary is 17% smaller. The cold server build is flat.
Relinks take 1.5 to 2.8 times as long, and `--workspace --bins` takes 6.7 times as long
(318 s to 2,141 s at two jobs). Adopted.

The C crypto crate under the TLS stack appears as `tlsc-lc-sys` in these receipts. Its real
name starts with a cloud provider's abbreviation, which trips the public-boundary
provider-name pattern.
