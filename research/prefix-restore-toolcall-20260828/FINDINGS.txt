A PREFIX-CACHE RESTORE ON glm5_next RETURNS AN EMPTY ATTENTION HISTORY
lane/prefix-restore-toolcall, 2026-08-28. Method and every stated deviation: METHOD.txt.
Parent evidence (12/12 cold vs 0/12 restored tool calls, cached_tokens 183/183):
research/glm53-flash-bringup-20260827/rebaseline-and-surface-20260828/ on lane/glm53-box.

================================================================================
1. THE MECHANISM
================================================================================

`PrefixEntry` (crates/memra-server/src/worker.rs) represents exactly TWO of the Cache's
state planes:

    kv    Vec<Option<PrefixPlane>>          ordinary full-attention K/V, copied per token
    conv  Vec<Option<CudaSlice<f32>>>       recurrent conv state, copied whole
    ssm   Vec<Option<CudaSlice<f32>>>       recurrent ssm state, copied whole

`memra_kv::Cache` has FOUR: `kv`, `recur`, `tp_kv`, and `latent`. The prefix-cache path
never mentions `latent`. Confirm it in one command:

    rg -n 'latent' crates/memra-server/src/worker.rs      ->  ZERO matches

`StatePlan::LatentKvCache` is where an MLA/DSA layer's FULL-ATTENTION history lives.
glm5_next declares 34 KDA layers (`StatePlan::Recurrent`) and 11 MLA/DSA layers
(`StatePlan::LatentKvCache`, crates/memra-gguf/src/model_packs/glm5_next/mod.rs:78,126).
The allocator (crates/memra-kv/src/lib.rs:1795) gives a LatentKvCache layer
`kv[il] = None` and `recur[il] = None`, so:

  CAPTURE  `prefix_snapshot` sees `kv[il] == None` for all 11 attention layers, records
           them as absent, and returns a valid-looking entry: `pos` at the prompt end,
           `toks` the whole prompt, boundary logits present. No error, no warning.
  RESTORE  `prefix_restore_at` copies the 34 KDA states, copies nothing else, and sets
           `cache.pos = restore_len`. Every latent plane stays at `len = 0`.
  DECODE   `HybridModel::mla_attn_cached` (hybrid_forward.rs:5393) takes
           `let slot = layer.len;`. It is 0. The first generated token is written to row
           0 and every MLA layer attends over a history of ONE row: itself.

So a "whole-entry hit" hands the model its recurrent gist and NO retrievable context, and
reports `usage.prompt_tokens_details.cached_tokens = N of N` while doing it.

THE SERVER LOG ALREADY CONFESSED IT, in a line the parent lane read as an operational
oddity (serve-B1.prefix-lines.txt):

  [prefix-cache] insert probation (seed):  96 tokens, 152.6MB
  [prefix-cache] insert probation (seed):  97 tokens, 152.6MB
  [prefix-cache] insert probation (seed): 319 tokens, 152.6MB
  [prefix-cache] insert probation (seed): 320 tokens, 152.6MB
  [prefix-cache] insert probation (seed): 325 tokens, 152.6MB
  [prefix-cache] insert probation (seed): 326 tokens, 152.6MB

Six prompt lengths spanning 3.4x, one constant entry size. The entry costs ZERO BYTES PER
TOKEN because it contains no per-token state at all: only the fixed-size KDA states. The
"two-entry prefix cache" the parent lane flagged is the same fact seen from the budget side.
The boot line agrees from a third direction: `[admission] "zai/glm-5.3-flash": plain
0 B/token`.

================================================================================
2. THE PROBE, AND WHY A FLUENT GUESS CANNOT PASS IT
================================================================================

latentprobe.py. Three probes, each with a bar that requires information the model can only
have from its context:

  tool    an UNGUESSABLE function name plus arbitrary required argument names plus an enum
          member: `zqx_fetch_glimb_status(vault_sigil="VS-7", glimb_mode="thrum")`.
          PASS requires all three exactly. No prior produces them.
  recall  a passphrase, QUARTZ-77-NIMBUS-4, stated ONLY in the user prompt, asked straight
          back. Tools are declared but irrelevant.
  bare    the same recall bar with NO tools block at all.

ARM DESIGN, and this is what the parent cell could not do: rep 0 of every cell is a COLD
prefill of the EXACT bytes reps 1..3 restore. Same boot, same prompt, same tools, same
sampler; the ONLY variable is the rep index. The parent cell's cold arm carried a unique
nonce prefix, so its cold and restored arms were not byte-identical and "the nonce did it"
survived as an alternative. It does not survive this design.

Greedy (temperature 0) is the instrument. Vendor-default sampled (NO temperature, NO top_p,
NO top_k, NO seed) is the product shape. `reasoning_effort` is PINNED low in every request.

================================================================================
4. THE FOUR HYPOTHESES THE BRIEF NAMED
================================================================================

H1 THE COUNTER LIES.  CONFIRMED, in a precise form. `cached_tokens` is truthful about the
   token count and false about the guarantee behind it: it counts tokens whose ATTENTION KV
   was never stored. The number is `entry.fed.len()`, which is real; the KV behind those
   tokens is the empty set.

H2 A DIFFERENT REQUEST SHAPE.  KILLED. The key is the whole rendered token sequence and the
   tools block is inside it. rep 0 and reps 1-3 send byte-identical bodies in the same boot,
   so no shape collision is available.

H3 A FULL HIT SKIPS SOMETHING PREFILL DOES, THINK-STATE FLAVOUR.  KILLED as stated, and
   subsumed. The `recall` and `bare` probes carry no tools, no tool wire and no dependence
   on `</think>` placement, and they fail identically. A wrong think state does not erase
   recall of a passphrase. What a full hit skips is not a template step: it is the entire
   attention history.

H4 OFF BY ONE AT THE BOUNDARY.  KILLED. The error is not one row, it is all of them
   (`len = 0` against `pos = N`), and the coordinator's production probe shows the shared
   boundary is sound on ordinary-KV models.

================================================================================
5. EXPOSURE, AND WHY PRODUCTION IS NOT AFFECTED
================================================================================

The mechanism is keyed on ONE property: does the ModelPlan declare
`StatePlan::LatentKvCache` for any layer?

    rg -n 'StatePlan::LatentKvCache' crates/memra-gguf/src/model_packs/
      glm5_next/mod.rs   (GLM-5.3-Flash)     support: NativeReference
      glm_dsa/mod.rs     (GLM DSA family)    support: NativeReference

No other pack declares it. `deepseek_v4` declares `StatePlan::CompressedAttention`, which
the native allocator refuses outright, so it cannot reach this path. Every qwen/gemma/step
pack uses `StatePlan::KvCache` or `SlidingKvCache`, which `prefix_snapshot` copies per token
and `prefix_restore_at` restores per token: unaffected by construction.

PRODUCTION IS STRUCTURALLY SAFE, WHICH IS A STRONGER CLAIM THAN "WE TESTED TWO MODELS".
The mechanism is not a probability that a served model trips this; it is a case analysis over
`StatePlan`. `prefix_snapshot` copies `KvCache` and `SlidingKvCache` layers per token and
`prefix_restore_at` restores them per token, so for any plan built only from those two the
entry IS the whole attention history and a whole-entry hit is exact by construction. The
defect requires a plane the entry has no field for. NO SERVED CONFIGURATION CAN REACH IT,
whatever the prompt, the sampler, the concurrency or the hit depth.

RECONCILED WITH THE COORDINATOR'S PRODUCTION PROBE, explicitly, because they asked. Their
result (qwen/qwen3.8-27b 4/4 and ornith-ai/ornith-1.5-35b-a3b 4/4 emitting the unguessable
call on full-prompt hits, cached 336/336 and 310/310) is PREDICTED by this mechanism, not
merely tolerated by it. Both models keep their attention history in `cache.kv`, which the
entry carries in full, so the mechanism REQUIRES them to pass; a red result there would have
falsified this diagnosis rather than extended it. That is the difference between "two models
passed" and "no served configuration can hit this", and only the second one is worth acting
on. It is also what rules out any explanation living in the shared restore boundary, which
both families use identically.

So: NOT a production incident. It IS a rollout blocker for glm5_next, because it silently
corrupts every repeated prompt, which is the agent shape we sell, and it corrupts it into a
confident wrong answer rather than an error.

WHAT IT RETROACTIVELY EXPLAINS in the parent lane, all of which should be re-baselined with
the cache off before anyone treats them as model properties:
  * The cold-vs-restored byte divergence BOX-STATE.txt recorded as a known quirk
    (raw p5 cold 5113588f11c49d5e vs restored d2f40996290fe905). That was this bug, not a
    property of the checkpoint.
  * The "prompt idx 2 still degenerates" rows: rep 1 cold clean, reps 2-4 restored
    degenerate. Contaminated by the same mechanism.
  * The open, unquantified 25-40% degeneration rate. Its cell was already confounded by
    two-entry eviction; it is additionally confounded by this.

================================================================================
6. SECOND SEAM, SAME BLIND SPOT, FOUND WHILE CLOSING
================================================================================

`memra_kv::CacheSnapshot` carries `kv_len` / `tp_kv_len` / `conv` / `ssm` / `pos`, and
`Cache::rollback` rewinds exactly those. Neither mentions `latent`; the struct's own doc
comment enumerates the same two plane classes ("full-attn KV" and "GDN conv/ssm") that
`PrefixEntry` does. So the PLAIN-AFFINITY checkpoint (`maybe_plain_checkpoint` ->
`e.cache.rollback(&ckpt.snap, 0)`) would move a parked latent-bearing cache's `pos` back
while every MLA layer kept its longer `len`, and the next turn would append past the
boundary and attend stale rows. It did not fire in these cells (the log shows
"plain-affinity: declined (no checkpoint retained)" throughout), so this seam has a
CODE-LEVEL finding and no behavioural receipt. The fix closes it anyway, fail-closed.

Named and NOT fixed, because it is unreachable today: `Cache::rollback` is also the spec
rewind, and spec on a latent model would hit the same hole. glm5_next is EAGER-ONLY with no
drafter armed, so nothing can reach it now. It becomes live the moment a latent model gets
a spec arm.

Receipt gap worth one line: `kvprobe` digests `cache.kv` only, so on glm5_next it would
have reported a constant empty digest for a cache with a full latent history. The one
instrument that could have caught this at the KV level is blind to the same plane.

================================================================================
7. THE FIX PROPOSED, AND THE DESIGN QUESTION HANDED UP
================================================================================

PROPOSED NOW (small, fail-closed, in the diff on this branch): a named predicate
`unsupported_prefix_state_plane(has_latent_plane)` and three call sites.
  * `prefix_snapshot` refuses the capture, so no such entry can exist.
  * `prefix_restore_at` refuses the restore, so an entry minted by any other publish site
    cannot land in a latent-bearing cache.
  * `maybe_plain_checkpoint` declines to arm, closing the second seam above.
Models without a latent plane take `None` from the predicate, so their path is unchanged.

THE GATE:
  * unit  `a_latent_bearing_cache_is_refused_by_the_prefix_capture`, and the 34 existing
          `prefix*` tests still pass (0 failed).
  * box   B1 vs B5 above: same cache configuration, 0/18 restored to 18/18 restored, with
          24 refusal lines and 0 hits in the server log.
  * The refusal is LOUD by construction: it prints
    "[prefix-cache] snapshot failed (latent (MLA/DSA) KV planes are not carried by prefix
    entries); prefix not cached" on every capture, so nobody has to infer it from a counter.

THE COST, STATED: glm5_next loses cross-request prefix caching entirely until the design
question below is answered. On this box that costs the ~13.4 s TTFT saving a hit was
producing. It was producing it by serving a wrong answer.

HANDED UP, because it is a design decision and not a patch:
  Carrying latent planes in a PrefixEntry is not a symmetric addition to the existing loop.
  * `LatentKvLayer::rows` is f32 and deliberately UNQUANTIZED (the maxdiff gate against the
    f32 `memra_engine::mla` oracle depends on it), so an entry grows by
    11 layers x width f32 per token, against a `kv` plane's quantized bytes.
  * `index_rows` is a TAIL RING (`MEMRA_DSA_INDEX_RING`), not a flat addressable plane, so
    it cannot be copied by absolute row like `kv`.
  * `index_pool_keys` / `index_pools_ready` are lazily built resident derived state with an
    append-only finality invariant. They must either travel with the entry or be rebuilt on
    restore, and `truncate_index_pool_keys` exists precisely because a `len` that moves
    backwards invalidates them.
  * The eventual acceptance bar should be stated up front: restored-vs-cold BYTE IDENTITY
    on the glm5 raw `/v1/completions` probes, which today diverge (5113588f11c49d5e vs
    d2f40996290fe905). Not "the tool call came back".
  The same lane should decide whether `CacheSnapshot` / `Cache::rollback` grow latent
  awareness or stay explicitly two-plane with the guard as the permanent contract. The
  coordinator has ADOPTED the byte-identity acceptance bar above; the work itself is the
  owner's call and is not started.
