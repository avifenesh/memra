ITEM 3  COLD-VERSUS-RESTORED BYTE DIVERGENCE   STATUS: SETTLED TWICE OVER, IT WAS THE CACHE
--------------------------------------------------------------------------------
BOX-STATE.txt records that on this model a cold first request differs in bytes from a
prefix-restored one, and the parent lane's METHOD.txt promoted that to a protocol rule:
"Every comparison here is therefore restored-to-restored or cold-to-cold". It was treated as
a property of the engine on this model.

It is this defect, and the evidence is already in this lane's banked receipts. Greedy is
byte-deterministic, so within one boot two identical greedy requests can only differ if the
ENGINE STATE differs. out_sha16 per rep, three prompts, four reps each:

  arm                     tool cell                          recall / bare cells
  B1 base, cache ON       e3b0c442 / 0e784782 x3             71aeec48 / 5fc567c9 x3
                          (rep 0 cold, reps 1-3 restored: TWO shas, exactly the divergence)
  B2 base, cache OFF      e3b0c442 x4                        71aeec48 x4     ONE sha
  B5 patched, cache ON    e3b0c442 x4                        71aeec48 x4     ONE sha

Cold and restored are byte-identical the moment a restore cannot happen, and the cold sha is
the one that survives. So the divergence was never a property of glm5_next: it was the
restore serving a different program. The parent lane's restored-to-restored comparison rule
was a correct workaround for a defect, not a law about the model, and it is retired with the
defect.

R3 RESULT (2026-08-29, cache off, raw /v1/completions greedy, the parent lane's own
attribution discriminator): p5 one sha (0e6d22ebc3787fc9) across 4 reps, p7 one sha
(e5b7fc011a0d4d9e) across 4 reps. With no restore possible there is exactly one greedy tape
per prompt, which is what "the divergence was the cache" predicts and what "an engine quirk
of this model" forbids. STATED SO NOBODY MISREADS THE NUMBERS: these shas are not comparable
to the old bank's values, because the binary is the merged head rather than the old lane
head and this cell's max_tokens is its own; the claim is the WITHIN-CELL identity, not a
cross-bank match. The cross-host, same-commit attribution is the epilogue lane's receipt,
absorbed rather than re-derived: R2's exact commit with restore ON reproduces the old banked
shas (4ec98d8aeb7a30e6 etc.) and with restore pinned OFF produces the merged head's shas
exactly. So the old sha bank carries pre-guard restore contamination, and the cold shas are
the honest bank going forward.
