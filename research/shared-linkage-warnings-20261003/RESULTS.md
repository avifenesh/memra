# Remove DSv4 dynamic shared-array linkage warnings

NVCC 13.1.115 emits warning 1556-D when the same extern dynamic shared-array name occurs under mixed enclosing C and C++ language linkage. A real four-arm compilation emitted the warning only for mixed linkage. Same-C, same-C++ and unique-name controls were silent. Mixed and unique-name sm_120a cubins were byte-identical.

The repair changes eight identifier occurrences in three functions. It names the numeric row top-k array topk_row_keys, the indexer helper array indexer_head_sums, and the templated dots array dots_row_sums. Reversing those exact renames reconstructs the original source byte for byte. Types, arithmetic, barriers, launch dimensions, dynamic shared-memory sizing and compiler recipes are unchanged. Diagnostics are not suppressed.

The actual original and repaired production translation units were compiled with the original build.rs recipe for 89, 90a, 100a and 120a. Each original emitted 16 diagnostics at eight unique sites. Each repaired target emitted none. All SASS/resource lines, instruction/data/shared sections and relocation bindings are exact. The allocated section counts are 1211, 1204, 1208 and 1208.

Whole cubin and fatbin identities differ. Exactly three compiler-local string labels change from $str$9/10/11 to $str$1/2/3, with identical symbol indices, type/binding/visibility, backing bytes, offsets and sizes. Blackwell's matching MERC symbol records carry the same three changes. Every other section payload and logical attribute is exact. Target89 also shifts 819 serialized metadata/constant file offsets by eight bytes and grows non-section zero padding from 108 to 116 bytes before the first code section. Allocated section memberships/permissions and bounds remain valid; every code section's physical offset stays fixed. Other production targets have exact program headers and physical offsets. All p_vaddr/p_paddr values are zero: this is a CUDA representation census, not an ordinary process-ELF virtual-load argument or a generic CUDA-loader qualification.

Six repaired native harnesses compile without warnings and execute all 18 unset/ON/OFF CPU controls. Their twelve actual native images and the six pinned assemblies of their actual sm_120 fallback PTX preserve instruction/data/shared/ABI sections. Six initializer images are byte-identical. R4 has a separately bounded representation change: one 128-byte read-only segment changes file offset by eight bytes while preserving its bytes, virtual fields, size and permissions. Non-section zero padding grows 96→104 bytes in the native image and 104→112 bytes in the fallback assembly. No physical change is normalized away.

The linked harnesses move relative unwind and exception metadata when their fatbin sizes change. The reader decodes CIE/FDE PCs, CFA bytecode, frame-header indexes, LSDA call-site/action bytes and type-pointer targets. All six decoded unwind/exception ABIs match. The original six harnesses were rebuilt at the identical worktree/source spelling. Every static symbol index is preserved after binding three relocated frame/ABI markers, and the private-name path ambiguity is absent. All24 original extracted cubin/PTX images are byte-identical to the earlier baseline, binding the existing device comparisons to these same-path builds.

The strict readers reject actual native mutations to instruction bytes, data, ABI fields, shared-memory layout, ELF identity, segment permissions/addresses/sizes, local symbol binding/size/names, unwind encoding/targets, CFA instructions and LSDA type-pointer targets. Unknown structures or differences refuse evidence admission. Failed strict attempts and whole-file hashes remain retained.

No CUDA context, model, rental, production host or owner accelerator was used. This maintenance evidence grants no 89 hardware, model, runtime, serving or multi-card qualification. The existing planner retains its full native obligation for a .cu edit. This issue's explicit acceptance alternative is the actual preservation of instruction/data/shared-memory/ABI evidence.

CUDA 13.1 documents dynamic shared memory as an external array sized at launch: [language extensions](https://docs.nvidia.com/cuda/archive/13.1.0/cuda-programming-guide/05-appendices/cpp-language-extensions.html#shared-memory). The linkage diagnosis comes from the real pinned compiler controls. NVIDIA documents the binary extraction/section/SASS/resource tools used here in [CUDA Binary Utilities](https://docs.nvidia.com/cuda/archive/13.0.3/cuda-binary-utilities/index.html).

The five compiler logs ending in a blank diagnostic line use lossless gzip storage. `raw-log-custody.json` binds their raw byte lengths and hashes; gzip roundtrips were checked. The exact uncompressed outputs remain in private custody.
