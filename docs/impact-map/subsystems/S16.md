## S16: model-specific and support CUDA kernels

**Scope.** This slice holds 30 CUDA files built two ways.

- **Fatbins** loaded by name into every `Engine`: `hybrid.cu`, `kda.cu`, `moe_router.cu`, `spec_sample.cu`, `tier_receipt.cu` (build.rs:212-234).
- **The static archive `libmemra_mmq.a`**, reached through C launchers: `dsv4_gpu.cu` (plus its headers), `dsv4_sampler.cu`, `moe_f16_grouped.cu`, `tp_ar.cu` and 15 `mimo_*.cu` files (build.rs:479-545).
- **`dsv4_dense_cutlass.cu`**, linked only on the `120a-MEMRA_DSV4_CUTLASS` variant through a weak symbol (dsv4_gpu.cu:4829).

**What reaches which family.**

- **`dsv4_gpu.cu` is not deepseek_v4-local.** About 9.9k lines carry the Dsv4Gpu trunk: compressor, indexer, sink attention, sqrtsoftplus/hash routing, fused MoE, replay. The HC section is shared with the glm5_next hyper-connection trunk through `hyper.rs`:
  - the unfused pre-chain `rowsq_scale`/`hc_sinkhorn_m`/`hc_collapse` (1146-1259, 5718-5779), which is the default on every non-100a build (hyper.rs:354);
  - the fused pre v1 to v4 kernels (6086-7426), which only glm5_next calls, on by default only on B200 (hyper.rs:353; v4 at 7405);
  - `hc_expand` (4038), which glm5_next alone calls.

  `memra_dsv4_nvfp4_deq_bf16` (168) also reaches qwen4_exp, and `fp4_gemm`/`act_quant_fp8` reach the mimo_v2 probes. The whole TU builds with `-fmad=false` (build.rs:674), so the research `MEMRA_DSV4_FMAD` build silently forks glm5 HC numerics too.
- **Hot dsv4 dense dispatch** is `memra_dsv4_gemv_fp8_m` (4876). It has four arms, and each is a numeric-class boundary:
  - dense-fast for m=2..16 (verify rounds), default on (4890);
  - the M=1 exact tail (4914);
  - the exact FP8 tile for m>32 prefill, which is skipped when the CUTLASS archive is linked (4922);
  - the scalar fallback.

  The doors are parsed host-thread-locally in `dsv4_dense_m1_exact_tail.cuh:14-63`. The HC24 S16 split-dot class (581-690) is default-on for every row count, so spec matches plain (#660).
- **`hybrid.cu`.** About two thirds is GDN (qwen35/qwen35_moe only; qwen4_exp uses its own scan in kernels.cu): conv, scan, chunk scan (38-969, 1298-1616), the bf16-HMMA chunk scan (1739-2361; default on 120a and Hopper, off on B200, absent on sm89) and Hopper wgmma (2391-2714). Family-specific pieces:
  - step35: the separate attention gate (999) and post-clamped SwiGLU (1025);
  - glm5_next: pre-clamped SwiGLU (1050);
  - FusedQ families: `q_gate_split` (1283).

  The generic helpers (`axpy`, `gather_rows`, `reduce_slots`, `sigmoid`, and `f32_to_bf16_bulk`, which feeds fa_prefill) make the file-level reach "all families".
- **`kda.cu`** is glm5_next only. The fused conv (132) and o-norm zq8 (314) are B200-default doors.
- **`moe_router.cu`** splits by router kind:
  - softmax top-k (24): qwen3_moe/qwen35_moe/olmoe;
  - sigmoid with bias (516): glm5_next/minimax_m3/hy3/glm_dsa/step35;
  - gemma scaled (606): gemma4_moe;
  - host-expf activation and EP staging twins (212-515): step/hy3 TP-EP;
  - the fused router (724-885): only behind the expired `MEMRA_ROUTER_FUSED`.
- **`spec_sample.cu`** reaches every HybridModel family: sampling, filtering, penalties, the grammar mask and round-stream spec bookkeeping. The cooperative `filter_stats` is the program on every card with at least 16 SMs, and its own comment says it is a different numeric class from the single-block kernel (447-460). It is not "bit-identical, speed only".
- **`moe_f16_grouped.cu`**: the f16-mirror grouped MoE prefill is default mode 2 on all arches (lib.rs:268). It reaches every MoE HybridModel family on prime and chunked prefill, step TP/EP, and the dsv4 grouped path. The `moe_kq_*` stream kernels (2374-2681) are dsv4-only.
- **`tp_ar.cu`**: glm5 TP peer push (110) and the dsv4 2-card EP joins (555-745). The second is default-reached because dsv4 serves on two cards.
- **`tier_receipt.cu`** runs only under `MEMRA_KV_HOST_CONTRACTS=1`. Its effects are policy and observability.
- **The mimo files** have no serving route: memra-server never references mimo, and mimo_v2 is not in PACKS.

**Where the impact set is wide and why.**

- `hybrid.cu` and `spec_sample.cu` are one module each with generic helpers, so file-level edits reach everyone. Region labels narrow GDN to qwen35/qwen35_moe.
- `dsv4_gpu.cu` drags glm5_next, qwen4_exp and mimo_v2 into a file named for one family.
- `memra_pdl_chain_on` (dsv4_gpu.cu:8515) is a process-global switch that changes launch scheduling for every static-lib TU.

**Top findings.**

1. `MEMRA_DSV4_CUTLASS` builds an sm_120a-only object with no arch assert (build.rs:756/767). On a 100a build, every dsv4 m==32 prefill chunk would hard-fail with 40082.
2. The flags census scans only `.rs`. CUDA-side getenv doors escape it, and `MEMRA_MIMO_SPLIT_STAGE_TIMING` has no FLAGS row (mimo_mixed_attn.cu:530).
3. Expired doors: `MEMRA_ROUTER_FUSED`, `MEMRA_SHEXP_SWIGLU_ZQ8`, the dsv4 dense rollback seams and the replay-control component.
4. Decoupling: move the HC kernels out of the dsv4 TU.
5. Dead code: `gdn_p_bf16_masked`, `memra_dsv4_fp4_gemm_sel_g`, the f16g byte helpers.
6. Stale docs: in moe_f16_grouped.cu, dsv4_dense_cutlass.cu and dsv4_gpu.cu:2269.

Most of the stage-0 dead candidates are false positives. The SCIP graph misses function-local `extern "C"` blocks in dsv4_gpu.rs and macro-generated template launches.
