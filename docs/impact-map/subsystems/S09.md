# Multi-card slice: tp, tp_ar, tp_transport, glm5_tp*, pp, ep_map

## What the slice does

This slice holds every multi-card program in memra except the dsv4 stack. It has three families of code with different reach.

1. **Step / generic TP-EP runtime (`tp.rs`, 15.9k lines).** `TpE4m3HostBounce` runs rank-local E4M3, BF16 and NVFP4 projections and routed experts on distinct CUDA devices. It is built only by `StepParallelRuntimeRegistry::runtime`, which refuses any device not named RTX PRO 6000 Blackwell (hybrid.rs:225). Every runtime method is therefore `rtxpro6000`-only. The runtime is reached through explicit `MEMRA_STEP_TP` / `MEMRA_STEP_EP` recipes or through `MEMRA_PARALLEL=auto`. The auto path is plan-generic (`ModelParallelContract::from_plan`), so expert paths reach any routed-MoE family through `moe_ffn_inner` (hybrid_forward.rs:12655, 12824). TP attention needs Full/SWA attention with one head_dim on every layer (parallel.rs:552), which excludes the GDN, KDA and MLA families. Hot paths:
   - decode-v2 attention (tp.rs:6103-8079);
   - NVFP4 device routes with prejoin (13602) and the default-ON SEL_DOWN8 fused down+combine arm (12528);
   - TP grouped prime (13061);
   - the automatic W4A16 EP walk (11385-11837), with W4A8 (11621) and pair-down (11710) sub-arms;
   - the distributed TP KV cache (2192-2844).

   Two doors default ON inside the TP cell: `MEMRA_NVFP4_BANK_SM` and `MEMRA_NVFP4_SEL_DOWN8` (tp.rs:395, 428), along with `MEMRA_ROWS_TAB_RESTAGE` (253) and the step37 tri-state `MEMRA_SPEC_FA2` (276). Everything else is a strict 0/1 default-OFF door.

2. **glm5_next TP-N (`glm5_tp.rs`, `glm5_tp_sampler.rs`, `glm5_tp_sym_graph.rs`, `tp_transport.rs`, `tp_expert_split.rs`, `ep_map.rs`).** The loader builds the view only for KDA/MLA plans and refuses everything else (hybrid.rs:4489). The preflight refuses PP, step TP/EP, three unproven decode doors and rank counts outside {2,4} (glm5_tp.rs:605-768). KDA layers are head-sharded with column-parallel `wo` (`kda_tp_cached`, 1399). MLA layers shard per-head operands and replicate the latent and indexer planes. MoE layers run whole-expert EP with an optional measured `memra-ep-map-v1` placement, or half-expert splits under `MEMRA_GLM5_TP_EXPERT_SPLIT` (a named partial-sum class). Transport is a separate axis: host-canonical by default, plus peer-pull and device-push (tp_transport.rs:150). The axis is byte-identical by construction because every hop is pure movement. `tp_ar.rs` supplies the one-shot all-reduce kernels. They are also consumed directly by the deepseek_v4 TP/EP stack (dsv4_ep.rs:494, 643), whose EP defaults to `pair` under TP/EP placement (dsv4_gpu.rs:3635). So `tp_ar.rs` FFI and `ar_blocks_for` changes can reach the dsv4 serving route.

3. **Pipeline parallel and the generic cache plumbing (`pp.rs`).** PP is gated by `pp_cuts` (MEMRA_PP_STAGES>=2, pp.rs:119). Once the door is open, several sub-doors default ON:
   - dual-active PP-2 (Auto, pp.rs:568/600);
   - boundary overlap;
   - prime split and prime pipeline;
   - spec verify split;
   - the peer probe.

   The PP3/4 wavefront is strict opt-in. The widest part of the slice is not PP, though. `new_cache_inner`'s default arm (3477), `layer_engine` (3517) and `restore_cache_checkpoint` (3661) run for **every family on every admit and prefix restore**. The SWA ring arm (3715) reaches the gemma4, step35 and mimo families, the recurrent arm (3867) reaches the GDN/KDA families, and the TP mirror arm (3806) reaches step TP.

## Effects and width

- Numeric: TP prime and decode paths, EP walks, the shard mechanics, the glm5 device sampler (different RNG program), the expert split, and the restore arms.
- Speed only (byte-identical by construction or gate): transport arms, graph doors and the scheduling doors (`MEMRA_ROUTES_PRESTAGE`, MOE_DIRECT, FENCE_MEMOPS, LEN_MIRROR_LAZY).
- Device narrowing is strong for `tp.rs` (PRO 6000). It is absent for glm5_tp: receipts exist on B200 pairs and PRO 6000, and the code has no device check.

The impact set is wide for two structural reasons. `pp.rs` carries the all-family cache and restore path, and `tp.rs` carries thread-local seams that `decode_step_h` reads for every family (decode.rs:820). The decoupling findings cut both.

## Top findings

- **Capture-failure parity bug** (glm5_tp_sym_graph.rs:547). After a partial capture, the KDA host ping-pong swaps sit at odd parity. The eager fallback, which the code calls byte-identical, can then read a stale recurrent buffer. The door is default-OFF.
- **Block-alignment check** (glm5_tp.rs:867). `shard_cols` uses the byte-divisibility test that tp_expert_split.rs:196 shows is insufficient.
- **Inconsistent cutlass refusal**: `shard_cols` drops a cutlass operand silently (glm5_tp.rs:846), while `shard_rows` refuses it.
- **Divergent PP door parsing** (pp.rs:306). A PP door that `pp_cuts` turned OFF can still trigger the unsplit refusals.
- **Stale doors past decide-by**: MEMRA_TP_AR_1STAGE, MEMRA_GLM5_TP_SYMMETRIC and MEMRA_GLM5_TP_EXPERT_SPLIT (2026-09-20), SYM_GRAPH (09-21), DEVICE_SAMPLE (09-22) and the TP transport arms. MEMRA_RANK0_MERGE has a NEGATIVE receipt and is still read in decode.rs.
- **Dead code**: about 18 unreferenced entry points (tp.rs, tp_ar.rs, glm5_tp.rs, tp_transport.rs). The one-shot collectives and the three host oracles can each be merged.
- **Determinism**: hybrid_forward.rs:12383 records that the TP grouped prime is nondeterministic run to run. Under the one-numeric-program rule, any change to tp.rs:13061-13542 needs a serving-shape identity gate on a PRO 6000 pair.
