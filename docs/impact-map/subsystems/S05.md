## S05: hybrid loader, decode, batched decode, prime graph, parallel

**What it does.** `hybrid.rs` builds a `HybridModel` for every PACKS family except deepseek_v4. Dsv4 dirs go to Dsv4Gpu (`dsv4_serve.rs:3`), and the MLA loader refuses compressed-KV (`hybrid.rs:2399`). `model.rs` picks a resident layout for each tensor. `decode.rs` holds the eager per-session decode (`decode_step_h`, `decode.rs:779`) and a large driver set that only gates use. `decode_batch.rs` is the serving decode for every model outside the eager-only class. `hyper.rs` is the glm5_next mHC residual. `qwen_prime_graph.rs` is a carried-prime CUDA graph. `parallel.rs` holds the TP/EP/PP topology contract. `graph_update.rs` holds the graph exec-update helpers.

**Hot paths per route.**
- **batch** (default). `decode_step_batch_sampled_lean_masked_schedule` forks in this order (`decode_batch.rs:1173-1537`):
  - unqualified-rewrite eager rows, only with a rewrite bundle (1194);
  - hyper walk for glm5_next (1238), default on: `MEMRA_HYPER_BATCH` unset means batched (2638);
  - PP wavefront, dual or ppn behind `MEMRA_PP_STAGES` (1284);
  - B=1 eager-fusion opt-in (1352), off by default and never for GDN plans (4984);
  - exact-16 tier for B 9..16 (1386);
  - Gemma arm for gemma4_dense and gemma4_moe (1425);
  - step35 arm (1450);
  - the generic body for everything else (1491).

  All arms end in one shared epilogue: grammar mask, device penalty, device sampling, lean park (4682).
- **plain.** `decode_step_h` dispatches hyper, E4B, Gemma, PP and the step35 token graph (786-813). Otherwise it runs the serial walk with the cross-layer add+norm+q8_1 fusion (871-975). `residual_norm_ffn` and `ffn_swiglu_decode` are shared with spec and the drafters. The clamped-SwiGLU arm (261) serves minimax_m3, step35 and glm5_next.
- **prime / graph.** `qwen_prime_graph::supported` is the most specific predicate in the slice: built 120a, exactly 170 SMs, and a qwen35 27B dense shape (`qwen_prime_graph.rs:100-115`). So it is the desktop RTX 5090 only.
- **mtp / dflash / glm5_spec.** Load-time arms: the embedded MTP chain, the external draft head (`load_draft`), FR-Spec trim, and the glm5 DFlash2 drafter (`hybrid.rs:4904-5567`). All but the embedded chain are default-off doors.
- **tp / ep / pp / spill.** Step TP/EP preparation (`hybrid.rs:887-2186`) is gated to PRO 6000 by device name (225). Auto placement writes `MEMRA_PP_*` and `MEMRA_BF16_MMV` into the process env (827, 856). Residency picks resident experts or the SLRU cache from free VRAM (315-366).

**Device-specific parts.**
- b200: `MEMRA_HC_FUSED_PRE` defaults to V2 only on 100a (`hyper.rs:353`), and so does the glm5 RMS block 1024 (`hybrid.rs:5638`).
- h100: Hopper forces the Q8RP/KQRP mirrors on (5823).
- rtxpro6000: the `generate_with` graph key drops to 48 only at >=180 SMs (`decode.rs:3356`).
- rtx5090: card class keys pinned-host kind and max cards (`parallel.rs:35-60`).
- Every card: the f16 prefill mirrors, a separate numeric class, depend on free VRAM at load (`hybrid.rs:5880, 5985, 6295`).

**Why the impact set is wide.**
1. `load_from_source_impl` (2207 lines) runs for every family. It also writes process-global numeric defaults: RMS block, FA split ladders, FA v4 cap, MMQ stream-K and the step37 doors (`hybrid.rs:4273, 4307, 5592, 5599-5640`). In a multi-model process, one model's load order sets another model's numeric program.
2. The generic batched body serves ten families at every width.
3. `HyperTopology::from_plan` runs on every load, so `hyper.rs` cannot be glm5-only at file level. Only its kernel half is (region 146-1132).
4. `qwen_prime_graph::current()` is read by kernel launchers on every prime.

**Narrow parts.**
- `decode.rs` ~1640-3461 (dc, graph sessions, generate, lockstep) and `graph_update` `fa_plan`/`fa_apply` never run in memra-server. They feed run-gen and the graph gates.
- `moesd_target_forward` is bin-only.
- The overlap pending path has no callers.

**Top findings.**
1. Process-global per-model defaults (`hybrid.rs:5627`, latched by `lib.rs:1719`) make co-loaded models change each other's bytes (medium).
2. glm_dsa decode reaches the generic batched body and panics on its MLA mixer (`decode_batch.rs:3176`). `eager_only_model` covers only Gemma, E4B and hyper, and the worker comment admits the panic (`worker.rs:39388`) (medium).
3. The run-gen gate decodes through `decode_step_dc` (`decode.rs:3429`), the eager numeric class, while serving uses the batched body. The code documents an FP-composition gap between the two (`decode_batch.rs:796`), so run-gen does not qualify the served program (medium).
4. `generate_with`'s qwen dc door panics or errors on MLA and hyper GGUFs (`decode.rs:497`). `decode_step_dc_cap_masked` lacks the gemma and PP guards (`decode.rs:1976`).
5. Residency reserves no trunk bytes for safetensors sources (`hybrid.rs:264`).
6. `validate_step_pp_request` is never called.
7. Dead code: the pending path, the grouped topology plan, and nine wrappers.
8. Stale docs: `MEMRA_HC_FUSED_PRE` (`hyper.rs:317`), the `MEMRA_HYPER_BATCH` message (`decode_batch.rs:2640`), and the hyper batch width (`decode_batch.rs:2698`).
9. Decoupling: split the gate-only drivers out of `decode.rs`, and key the mirror arithmetic on card class rather than free VRAM.
