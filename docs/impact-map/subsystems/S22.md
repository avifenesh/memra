# S22: build scripts and gates

## What the slice does

The slice has two halves. The first is the build: `crates/memra-engine/build.rs`, with smaller build scripts for the server and probe crates. It decides which numeric program every binary carries. The second is the gate layer. That is the gate binaries `kernel_check`, `run_gen`, `run_spec` and `argmax_margin_probe`, plus the scripts that judge them: the release battery, serve-smoke, `validation_plan.py`, the fast-gate planner and qualification. Nothing in the gate half is linked into `memra-server`. A change there moves a verdict or the coverage (effect `policy`), never served bytes. The one exception is `run_spec` minting MtpSpec rewrite receipts that serving later admits (`run_spec.rs:562-578`).

## Engine build: the widest blast radius in the repo

`build.rs` reaches every family, route and device:

- `detect_arch` maps compute caps 12.0 and 12.1, a GPU-less build and any unknown cap to 120a, so gb10 rides the 120a build (`build.rs:174`, `:178`).
- It emits the `memra_portable_cuda` (89 and 90a), `memra_hopper_mma` (90a) and `memra_sm100_tcgen05` (100a) cfgs, plus `MEMRA_BUILT_CUDA_ARCH` (`:270-288`).
- It builds nine single-arch fatbins (`:290-335`).
- It builds a 36-TU static archive with per-TU device arms:
  - Off Blackwell, `mmq_fp4`, `mmq_nvfp4_w4a8` and `mmq_fp8_blk` are replaced by fail-closed stubs (`:556-587`).
  - On b200, the plain f8f6f4 forms and tcgen05 are forced (`:622-648`).
  - FA3 is real only on 90a (`:660`).
  - `dsv4_gpu.cu` compiles with `-fmad=false` (`:674`).
- The kf8vf8 flash module serves only the gemma e4m3 KV layers (`:337-374`, `lib.rs:4085`).
- `generate_env_registry` turns `docs/FLAGS.md` into the boot env audit (`:896-1125`). A FLAGS.md edit is therefore a policy change for every binary.

Most build-env seams default off (`MEMRA_MMQ_X_*`, `MEMRA_IQEXP_K16`, `MEMRA_MMQ_FOLD_CEILING`, `MEMRA_DSV4_FMAD`, `MEMRA_CUTLASS`, `MEMRA_DSV4_CUTLASS`), so they reach no default cell. The b200 forced forms are reached by default.

Narrowing trap: `dsv4_gpu.cu` is not DSv4-only. `hyper.rs` calls its `hc_*` kernels for the glm5_next hyper trunk (`hyper.rs:372`, `:1118`), and `mimo_source_moe.rs` also uses it. That TU's flags and its PDL header therefore reach glm5_next and mimo_v2 too.

## Gate binaries: which arm each family takes

- **run_spec**:
  - The plain oracle uses the live batched B=1 program for step35 (SlidingGatedMoe) and the GDN plans (qwen35, qwen35_moe, qwen4_exp), and a split step under PP. All other families use `generate()` (`run_spec.rs:70-117`).
  - It refuses headless artifacts (`:195`) and sweeps K=1..8 (`:441`).
- **run_gen**:
  - Directory checkpoints gate `decode_step_t` against tokenwise decode (`:468-537`).
  - GGUF gates `forward_last` against tokenwise, plus a batched `prime_cache` gate (`:1269-1300`, default on). Only GGUF gets that prime gate.
- **argmax_margin_probe** is the release argmax arm. It compares `forward_last` with decode only, and gives gemma4-31B a 3/12 flip budget (`:248`).
- **kernel_check** cells are family- and device-keyed:
  - The GDN cells reach qwen35, qwen35_moe and qwen4_exp, with the mma pin on 120a/90a and the wgmma pin on 90a only (`:1888`, `:1920`).
  - NVFP4 cells run on 120a and 100a (`:3286-3300`).
  - The step35 cells are the SWA prefill view, the head gate and the clamped SwiGLU. A glm5_next pre-clamp cell follows.
  - It also has softmax- and sigmoid-router cells and model-free PP policy cells.

## Release and dev gates: where coverage is narrow

- **Release battery.** It runs kernel-check with two required-cell manifests, then argmax-margin and run-spec on a two-row roster: Ornith-1.5-35B-A3B (qwen35_moe) and Qwen3.8-27B (qwen35), both NVFP4+Q5_K. `release_qualification.py:394` binds the expected cells to that roster. A tag PASS therefore covers no gemma4, step35, glm5_next, deepseek_v4, hy3 or FP8_BLOCK cell. Step35 has a separate hash-bound step-pro hook (`check_hardware_gate.py:16-18`).
- **Fast-gate.** It is shadow-only, its goldens were minted on the 82-SM 5090 (`models.tsv:36`), and they date from 2026-08-02..05, before the 120a GDN-MMA default flip. Its DEFAULT/expansion probe set covers only gemma4 and the qwen35 class (`map.tsv:148`).
- **validation_plan.py.** It sends every `.cu`, `.cuh` or `build.rs` change to the full battery (`:1166`, `:1284`) and correctly registers `docs/FLAGS.md` as a memra-engine input (`:1099`).

## Top findings

1. **Stale kernels after a header edit.** `build.rs` never lists `memra_pdl_chain.cuh` or `dsv4_dense_census.cuh` in rerun-if-changed (`:547-555`). Editing either does not rebuild the DSv4 chain, the glm5_next hc kernels, the MoE f16 grouped GEMM or `tp_ar`, and the gates test stale kernels.
2. **No prime gate in the release battery.** It never gates `prime_cache` against tokenwise decode (gap #46 lives only in run_gen).
3. **Two-model roster.** The release roster has two models, while AGENTS.md:118 promises every board model.
4. **Fast-gate DEFAULT under-covers.** It cannot reach dsv4, glm5, hy3 or FP8 code. Its e4b probe targets a family both gemma packs refuse.
5. **MEMRA_DSV4_CUTLASS.** It hardcodes sm_120a with no arch assert (`:767`) and has no FLAGS.md row, because the census skips `build.rs`.
6. **Small defects.**
   - run_spec decodes MEMRA_PRINT_TEXT with `path` instead of `tok_dir`, which breaks on Hy3 repack dirs (`:422`).
   - The sampled-mode failure report diffs the wrong pair and can panic on `unwrap` (`:518`).
   - Stale docs: `serve-smoke.sh:8`, `release-battery.sh:199`, and the FLAGS.md row for `MEMRA_MMQ_X_Q45K`.
