# Release profile: opt-level 3, fat LTO, one codegen unit (2026-11-02)

**Status:** adopted. The workspace `Cargo.toml` carries `[profile.release]` with `opt-level = 3`,
`lto = "fat"` and `codegen-units = 1`, the owner's standard release profile for Rust repos. Before
this the workspace had no profile section, so release builds used Cargo's defaults (opt-level 3,
16 codegen units, thin-local LTO). Receipts: `research/release-profile-20261102/`.

## What the profile can reach

The profile changes how rustc optimizes and links Rust code. Each part of memra was checked for
whether that reaches it.

- **CUDA kernels: not reached.** `crates/memra-engine/build.rs` (and the `memra-probe` and
  `memra-server` build scripts) call nvcc with fixed flags (`-O3`, the gencode, the MMQ tile
  defines). None of them reads `PROFILE`, `OPT_LEVEL` or `DEBUG`. Measured: all 11 fatbins are
  byte-identical between the two profiles. `libmemra_mmq.a` differs by 6 bytes per object, which
  is nvcc's per-run temporary file name (`tmpxft_<pid>_..._<src>.cudafe1.cpp`) embedded in the host
  stub; the 33 device ELFs inside it, extracted with `cuobjdump -xelf all`, are byte-identical.
  The 6-byte difference appears between any two nvcc runs, with or without a profile change.
- **Native C and C++: not reached.** The TLS stack's C crypto crate (named `tlsc-lc-sys` in the
  receipts, because its real name trips the public-boundary provider pattern) compiles C through
  the `cc` crate, which reads `OPT_LEVEL`; opt-level stays 3, and its archive is byte-identical
  between the arms. The CPU expert
  companion (`tools/memra_cpu_experts.cpp`) is built by its own script with `-O3 -march=native` and
  is loaded at run time, outside rustc. Rust LTO covers Rust LLVM bitcode only; nvcc and gcc objects
  are linked as they are.
- **Build scripts and proc-macros: not reached.** They compile under Cargo's `build-override`
  defaults, and LTO is never applied to them.
- **Rust CPU code: reached.** That covers the server (HTTP and SSE, JSON, template rendering and
  BPE, admission, scheduler and worker tick), host-side sampling, GGUF and safetensors parsing and
  host dequant, the reference executor (`memra-reference`) and the Rust side of the CPU expert
  path. Cross-crate inlining is the mechanism: before this, tokenizer, sampling and engine code
  could not be inlined into the server crate's callers.
- **Numerics: unchanged by construction, and measured.** rustc does not contract `a*b+c` into an
  FMA or reassociate float operations unless code asks for it explicitly, and LTO and inlining
  preserve IEEE semantics, so the same source computes the same bits. Measured: the CPU crate suites
  (reference, sampling, tokenizer, gguf, validate: 624 passed) and the engine lib suite (674 passed)
  pass in both arms, including their bit-exact golden assertions; `cpu_native_check` prints identical
  expected and actual values; `/v1/tokenize` on a 165,525-token chat returns identical ids; a greedy
  512-token stream and a seeded sampled 256-token stream are byte-identical across both arms and all
  rounds.
- **Debug assertions, overflow checks, panic strategy: unchanged.** The release defaults stay:
  `debug-assertions = false`, `overflow-checks = false`, `panic = "unwind"`. The workspace has no
  cdylib or staticlib crate, so no crate needs an `lto` override.
- **Profiles that inherit it:** `bench` inherits `release`, and `cargo test --release` builds with
  the release profile, so CI's `cargo test --release` jobs now build fat-LTO test binaries.
- **Release qualification: reached, as by any `Cargo.toml` change.** `Cargo.toml` is a tracked
  release input and the binaries' bytes change, so existing qualification records do not cover the
  new binaries; the next tag needs a native qualification run on the new bytes. The
  `.cargo/config.toml` contract (`[build] jobs` only) is untouched.

## Decision

Serving on the 5090: TTFT, short-request E2E and greedy decode are flat, moving by less than the
spread between rounds. Tokenization is faster: in the 60-call rounds, the 165,525-token
`/v1/tokenize` median drops 6.3% (server CPU per call drops 4.0%), and the fat-LTO arm is faster
in all three interleaved pairs. The 20-call rounds were too noisy to show that difference (-1.3%).
Boot is about 5% faster, but that rests on three rounds per arm with a cold-cache first round. The
decode worker spins while the GPU works, so decode measures GPU-bound wall time and does not
isolate host work. Every correctness surface is byte-identical. The server binary is 17% smaller.

Build cost is the link. Each binary now gets its own whole-program optimization, so the cost
scales with how many binaries a command links. Measured at two jobs:

| command | default | fat LTO |
|---|---|---|
| cold `-p memra-server` | 499 s | 508 s (flat) |
| relink after touching the server | 61 s | 169 s (2.8x) |
| relink after touching the engine | 132 s | 203 s (1.5x) |
| the qualified gate binaries | 103 s | 184 s (1.8x) |
| `--workspace --bins` | 318 s | 2,141 s (6.7x) |

The last row is the CI full-mode build command, and the `cargo build --release` that
`docs/INSTALLATION.md` shows. The installation guide now names `-p memra-server` for a server-only
build.

Hosted CI (GitHub `ubuntu-24.04` runners, `ci.yml` full mode, first run of this change against
the four latest successful scheduled runs on `main`): `build` (every binary) took 59.6 min, against
12.0 to 18.0; `arch-coverage (100a)` took 45.6 min, against 11.6 to 19.5; `server-tests` took 20.0
min, against 11.9 to 15.1. That `build` time sits just under the job's 60-minute timeout. Jobs that
do not link release binaries (clippy, boundary, portable-suites, publish-dryrun) did not move. The
first run also started from a Rust cache built under the old profile, so dependency crates
recompiled; the binary links dominate either way, as the `--workspace --bins` row shows. Hosted CI
time is the open cost of this change. The ways to close it are a longer timeout, or a CI-only
profile override for compile-and-test jobs; the second would leave the fat-LTO bytes to release
qualification. Both are workflow changes and belong in their own lane.

Adopted. Runtime is neutral or better, no result changes, and the profile is the owner's standard
for Rust repos. The build cost is recorded here so it is not rediscovered.

`.cargo/config.toml` keeps `jobs = 6`. The setting caps concurrent rustc processes. Measured fat-LTO
peaks: 3.1 GB for one rustc linking `memra-server`, 1.2 GB per rustc across the workspace binaries.
Six concurrent links therefore fit both the rig and a 16 GB hosted runner. The rig's own builds run
at two jobs under the shared build lock (`CARGO_BUILD_JOBS=2`), and release qualification passes
`--jobs` explicitly. Nothing measured here argues for a different number.

Rejected: keeping Cargo's default release profile. It is not the owner's standard, and it is
slower on the one host path that moved (tokenization). Not built: a separate fast-link profile for
development loops. It would produce binaries that differ from the qualified ones, and that is a
separate decision for the owner.
