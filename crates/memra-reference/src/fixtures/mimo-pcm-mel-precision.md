# MiMo PCM to mel precision, 2026-09-27

The oracle generator in this directory calls `utils.py::mel_spectrogram` from
`XiaomiMiMo/MiMo-Audio-Tokenizer@b62b59922979bf9f389b373169298a251587653f`.
It uses the pinned V2.6 codec config with SHA256
`e0702adae37947e0c980c38bae58ffa0d48bd492d523afe814aa4d73f008c7d1`,
CPU torch `2.6.0+cpu`, torchaudio `2.6.0+cpu`, and one torch thread.
This torch build reports MKL available. The publisher package requires
`torch>=2.6.0` and `torchaudio>=2.6.0`, without fixing a numeric FFT backend.
The V2.6 model config names Transformers `5.3.0`; it does not define this mel
transform.

## Cause of the narrow-tone difference

The publisher calls torchaudio's `MelSpectrogram` with a centered reflect
pad, periodic Hann, unnormalized F32 STFT magnitude (`power=1`), 128 unscaled
HTK mel filters, and natural log after a `1e-7` floor. The generator manually
reassembled those F32 steps using the transform's actual window and filters.
Its output was bitwise equal to the publisher function on the sparse case
(max absolute log-mel difference 0).

`torch.hann_window(960)` matches the F32 tensor expression
`0.5 - 0.5 * torch.cos((2*pi/960) * arange(960))`. It differs from an F64
analytic Hann rounded to F32 by at most `1.7881393432617188e-7` (637 of 960
coefficients differ). At sparse-case mel 127, frame 4:

| Window and FFT arithmetic | Raw mel | Log-mel |
| --- | ---: | ---: |
| Publisher F32 Hann, F32 FFT | 9.693118954601232e-6 | -11.54409408569336 |
| Same F32 Hann and windowed samples, F64 FFT | 5.006208084523678e-6 | -12.204832077026367 |
| Analytic F64 Hann rounded to F32, F64 FFT | 2.8979518447158625e-6 | -12.751506805419922 |

The earlier direct F64 DFT and analytic window returned `-12.751498` there,
causing the reported `1.2074041` log-unit error. The table separates about
`0.6607` log units from FFT arithmetic and `0.5467` from window generation
at this nearly empty frequency band. Pinning the publisher's F32 window and
filter coefficients removes window and filter drift. We also tried a native
mixed-radix F32 FFT. It lowered the pure-tone difference but increased error
on accepted voiced and chirp cases. The retained direct F64 DFT gives smaller
errors on the accepted corpus. It still differs from torch's F32 FFT in
nearly empty bins, so it does not claim bitwise equivalence.

## Native F32 FFT route

Torch 2.6.0+cpu reports oneMKL `2024.2-Product Build 20240605`. Its
`libtorch_cpu.so` exports oneMKL DFTI symbols. The standalone `mkl==2024.2.0`
package provides `libmkl_rt.so.2` with the same build string. The native FFT
probe uses a single 960-point F32 real-to-complex DFTI descriptor, out-of-place
complex storage, and no normalization. Both libraries produced **bitwise
identical complex FFT results** to `torch.fft.rfft` for every frame in the
nine-case corpus. Applying the publisher's F32 mel matrix and log in Torch
then produced bitwise identical full log-mel outputs.

The installed system FFTW3f library was tested on the same F32 windowed
frames and publisher mel matrix. Its largest log-mel error was `0.694840431`
absolute and `0.0639984682` relative, both on the pure 440 Hz tone. It is
not a source-faithful replacement for this pinned Torch build. The
reproducible comparison is `mimo-pcm-mel-native-fft-probe.py`.

`MiMoPcmMelFrontend::compute_with_mkl` now calls a caller-supplied standalone
oneMKL `libmkl_rt.so.2`, checks the exact 2024.2 build string, and limits the
960-point descriptor to one thread. It does not load Torch. Its Rust F32
magnitude, mel accumulation, and log leave at most `9.536743e-7` absolute
and `0.00095144496` relative log-mel error on the full corpus, including
tones. The relative maximum is at a publisher log-mel value near zero.
This is a bounded CPU component proof. Packaging the native library and
qualifying other CPUs, Torch builds, codec tokens, and serving remain open.
No audio support state or serving flag changes.

The oneMKL corpus test is explicitly ignored without the standalone library:

```sh
LD_LIBRARY_PATH=/absolute/path/to/mkl/lib \
MEMRA_TEST_MIMO_MKL_RT=/absolute/path/to/mkl/lib/libmkl_rt.so.2 \
CARGO_BUILD_JOBS=2 cargo test -p memra-reference \
  standalone_one_mkl_matches_full_publisher_corpus_when_available \
  --lib -- --ignored --nocapture
```

## Diagnostic DFT contract

The explicit oneMKL path and the DFT diagnostic accept only 24 kHz mono F32
PCM with 481 to 24,000 samples. Silence maps exactly to the publisher's
`ln(1e-7)` floor. In the diagnostic DFT, a
non-silent clip is rejected when **any** raw mel magnitude is below
`1e-3 * max(abs(pcm))`. This cutoff separates the unstable sparse cases
from the tested broadband/noise/voiced/chirp cases. It is a fail-closed scope
limit, not a proven error bound for all waveforms. Diagnostic output from
rejected cases is available only inside the tests.

The seeded fixture corpus was generated by the pinned publisher function.
Errors in the following table compare the **diagnostic DFT** with its
log-mel bytes. Relative error is
`abs(native - publisher) / max(abs(publisher), 1e-6)` **after** the log.
The table gives the maximum of each metric across all mel bins and frames.
